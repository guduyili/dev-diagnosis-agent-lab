# DeepEval 与回归评测规范

## 1. 先定义“完成”，再选指标

知识诊断任务的成功需要：结论符合资料版本、证据支持结论、缺信息时正确澄清、未执行操作不声称已执行。
后续若加入测试执行，成功还需要命令退出状态、实际测试结果和符合需求的断言。

当前 `evals/` 没有实现，三个正式 JSONL 文件为空；`data/examples/` 是虚构的格式示例。

## 2. 数据集约定

- `dev.jsonl`：允许频繁查看，用于调参。
- `regression.jsonl`：已确认失败及核心行为，修改后复测。
- `holdout.jsonl`：冻结版本前才使用；按相同 bug/资料/改写问题家族分组，避免近重复跨集合。

首批可以收集约 30 条人工审核案例，例：15 开发、10 回归、5 保留。它只适合学习，不足以证明通用能力或稳定估计总体准确率。
每条用例必须有人审核输入、来源与预期；模型生成的数据必须标注来源并人工确认。

字段格式见 [用例说明](../data/cases/README.md)。`actual_output`、实测耗时和真实工具调用存运行结果，不能预先混在标准答案里。

## 3. 实施顺序

1. 实现 JSONL 加载器：校验字段、唯一 ID、审核状态和问题家族。
2. 实现 agent adapter：只给 Agent 输入部分，收集真实结果与证据。
3. 用纯 Python / pytest 做格式、状态、上限、引用来源存在性等检查。
4. 创建 DeepEval `LLMTestCase`：input 来自问题，actual_output 来自运行，expected_output 来自人工参考，retrieval_context 来自实际召回。
5. 工具记录转换为 `ToolCall`；区分“计划调用”“实际调用”“实际成功”，不要只取模型文本。
6. 先跑 1 条，再跑 5 条，最后全开发集。记录模型与评分器配置。
7. 用 `assert_test` 写需要阻塞发布的测试，显式运行 DeepEval。

未来创建 `evals/test_regression.py` 后，在项目根目录执行：

```powershell
.\.venv\Scripts\deepeval.exe test run evals/test_regression.py
```

当前该文件尚未创建，所以该命令现在不能用于验证项目。
DeepEval 官方将 `deepeval test run` 用于测试门禁；单纯收集实验分数不等于建立了失败退出策略。[CI 官方文档](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd)

## 4. 评分分层

| 检查 | 推荐方式 | 要避免的误区 |
|---|---|---|
| 引用指向实际存在的资料版本 | 确定性检查 | 来源存在不代表来源支持结论 |
| 工具调用名、必要参数、次数 | 程序断言 / ToolCorrectnessMetric | 工具名正确不等于参数、执行成功 |
| 回答是否覆盖问题 | AnswerRelevancyMetric + 人工抽检 | 相关不等于正确 |
| 结论是否由实际检索片段支持 | FaithfulnessMetric + 人工检查 | 有依据不等于资料本身最新或正确 |
| 诊断、澄清和不确定性是否合理 | 人工 rubric / 自定义 GEval | 裁判给高分不代替事实核验 |
| 测试执行是否完成任务 | 退出码、测试报告、业务状态 | 不以 Agent 最终文本为唯一依据 |

所列指标是后续候选，不要求同时接入。正式使用前按已安装版本核对参数。
`ToolCorrectnessMetric` 默认主要比较工具名；需要时配置输入参数/输出要求。部分模式涉及 LLM 裁判，不能笼统认定全部免费或完全确定性。[工具正确性文档](https://deepeval.com/docs/metrics-tool-correctness)

## 5. 裁判校准

先人工评 10 条，包括明显正确、明显错误、部分正确、应澄清四种情况，再与模型评分比较。
记录分歧，修订评分标准并重新检查。生成模型和裁判可不同，但不同模型并不自动保证独立和正确。
模型评分需要明确配置 provider、模型与凭据；`.env.example` 的 EVAL_* 需要自己实现映射。Confident AI 云平台是可选项，不是建立本地评测的前置条件。

## 6. 报告必须同时包含

- 总任务数，以及 passed / failed / error / skipped / not_run。
- 完成判定覆盖率：实际得到有效判定的任务数 / 计划任务数。
- 业务成功数 / 计划任务数，以及业务成功数 / 有效判定任务数，两种分母写清。
- 按失败类型分层的结果；不可把空数据集或全 error 算作 100% 通过。
- 平均和 P95 耗时（样本很小时优先列原始耗时，并提示统计不稳定）。
- 模型调用、工具调用、token 与已知费用；裁判费用单独记录。
- baseline 与 candidate 的逐条变化：修好的、退化的、未改变的。
- 不适用的指标为 N/A；无工具调用任务不能随意记工具正确率为满分。

## 7. 非确定性与门禁

温度为 0 也不能保证所有服务完全确定。对波动的关键用例至少重复 3 次，保留每次结果与缓存状态。
首次没有足够样本时，语义分数先作为观察项。对实际稳定的关键用例再设门禁，并把阈值和设定理由写进实验记录。

建议初期门禁：普通测试通过；关键用例无已知新增业务失败；error 单独阻塞；跳过必须有理由并显示未覆盖；完成情况与费用预算符合本次预先定义。
不要靠降低阈值、标 flaky、删用例或放宽断言掩盖退化。确需调整标准时用独立变更解释原因。

## 8. 版本快照

每个实验保存：代码 SHA（若有未提交变更也要标记）、数据集版本/哈希、Prompt 版本、知识库/索引版本、模型设置、DeepEval 版本、评分规则、运行环境、重复次数、缓存策略、时间。

使用 [实验模板](templates/experiment.md)。早期报告写“学习实验”，不要据 30 条样本宣称生产可用。

基础参考：[DeepEval 入门](https://deepeval.com/docs/getting-started)、[DeepEval 仓库](https://github.com/confident-ai/deepeval)。数据划分、门禁与报告设计是本项目建议。
