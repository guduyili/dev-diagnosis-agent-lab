# 日常使用与长期维护

## 每天：让真实问题进入学习流程

1. 选择当天的一条研发问题，先记录时间、版本、错误现象和已有证据。
2. 自己提出一个假设，再让助手提供诊断；记录人工查阅和修正量。
3. 人工验证结论，标记解决/未解决/误导，不只评价文字是否流畅。
4. 失败经过复现和审核后才能加入回归集；未经确认的保留在问题笔记。
5. 用每日模板记录“一个收获、一个问题、下一步”。

## 每周：一次小迭代

- 选一类最常见失败，领取 backlog 中一个任务。
- 在修改前保存基线，再提出假设、实施、运行对比。
- 如果效果没改善，保留负面结果，解释可能原因；不为赶进度只挑好看的案例。
- 用周报总结，并更新进度表。

## 每月：保持可复现

- 查看上游与依赖变更，在独立参考环境验证。
- 检查知识过期、重复问题和数据划分泄漏。
- 抽样复核裁判，记录评分规则是否变化。
- 根据真实使用选择一个下月主题；不要同时重写前端、数据库和 Agent 架构。

## 发布前

1. 固定代码、模型、知识、Prompt、评分与数据版本。
2. 跑普通测试、必要集成测试和明确触发的模型回归。
3. 审阅失败、环境错误和跳过；关键项不满足就保留为未发布。
4. 保存逐条报告，填写发布说明中的已知限制。

第 7 周前没有自动 CI。届时先启用无模型的快速检查，模型回归采用手动触发，明确预算与凭据；本骨架没有预设付费自动任务。

## 测量提效

对于可比较任务，记录人工处理时长、助手处理时长、人工校正时长、最终是否解决。
不要只比较模型生成时间。简单任务与复杂任务分开，保留原始记录后再计算中位数和变化。
同一个问题第二次处理有记忆效应，不能直接把全部缩短归因于 Agent；注明顺序，后期用新问题或交叉实验验证。

## 三种岗位的成果表达

| 方向 | 展示重点 |
|---|---|
| Agent 开发 | 图与工具设计、异常恢复、上下文与来源追踪、质量/成本取舍 |
| Agent 评测 | 用例设计、裁判校准、实际任务成功标准、失败分层与复现 |
| 测试开发 | pytest、接口/报告工具、异常场景、CI 门禁、缺陷复现 |

简历句式（占位符必须用真实结果填写）：
“基于某上游版本扩展研发诊断助手，新增【个人模块】，建立【数量】条人工审核用例，在固定【配置】下观察到【结果】，并分析【局限】。”
