# 8 周学习与实现路线

目标：为自己的一个真实项目提供研发问题诊断，并通过回归评测证明改动是否有效。
建议每周 8–12 小时：2 小时阅读、5–7 小时实现与调试、1–3 小时评测和复盘。
下面的时长是学习计划估计；按验收结果推进，不为赶周数跳过关键步骤。

## 前置自测

不查完整答案，尝试：用 Python 读取 JSONL；捕获文件不存在异常；写一个 pytest 参数化测试；解释 HTTP 状态码；用 Git 查看 diff。
其中三项以上困难时，先用 1–2 周补 Python 文件操作、异常、类型提示、HTTP 与 pytest。暂时不学多 Agent 和复杂部署。

## 第 1 周：选场景、跑参考项目、建立问题记录

学习问题：一个问题从输入到检索、再到回答经历什么？

1. 选一个自己长期开发的项目，写三种高频问题和三项暂不支持的任务。
2. 按环境指南建独立 venv；克隆上游并记录 SHA。
3. 阅读上游 Notebook 和核心图，画出正常回答、澄清、检索不足三条路径。
4. 按上游说明跑一个最小例子；记录模型、embedding、依赖和实际异常。
5. 收集 5 条自己遇到的问题，先人工整理解决步骤和证据，不急于生成数据集。

交付：来源登记、环境记录、流程草图、5 条问题记录、周复盘。
验收：能解释 child/parent 分块与工具循环；至少记录一次真实运行或定位清楚的阻塞，未跑通不能写“通过”。
面试自问：为什么这里需要 Agent？单次检索是否已经足够？

## 第 2 周：知识整理、数据结构与普通测试

学习问题：什么样的资料可以成为可靠证据？

1. 选取 10–20 份自己的 Markdown/TXT 资料，记录来源、项目版本、更新时间。
2. 实现知识条目加载，设计稳定的 document_id/chunk_id；先保留代码块和异常栈结构。
3. 实现一种简单切分策略，输出可人工检查的 chunk，不急于优化模型。
4. 为文件缺失、空文档、重复资料、元数据丢失写普通测试。
5. 将 10 条人工检查过的问题整理为开发用例；明确哪些问题没有足够证据回答。

交付：知识加载代码、分块样例、确定性测试、10 条开发用例。
验收：任意检索片段都能追溯到具体版本资料；故意删掉必要元数据时测试应失败。
面试自问：同一错误在不同版本里的原因不一样时，知识库如何表示？

## 第 3 周：建立普通 RAG 基线

学习问题：错误来自检索不到、检索错了，还是生成过程？

1. 选择一个 embedding 配置，建立可重建索引，登记索引与知识库版本。
2. 实现检索接口，保留文档 ID、块 ID、排序与来源；手工检查 10 条查询。
3. 做“单次检索 → 生成回答”的简单基线，返回答案和证据。
4. 比较两种 top-k 或分块设置，每次只变一个因素，保存逐条输出。
5. 根据真实失败把问题分为知识缺失、召回失败、版本冲突、生成错误。

交付：普通 RAG、baseline-v1 报告、可复现的知识与模型配置。
验收：人工核查至少 10 条答案；证据不足时表达不确定性；不使用复杂 Agent 掩盖基础检索问题。
面试自问：为什么增大 top-k 不一定改善效果？

## 第 4 周：实现有边界的诊断 Agent

学习问题：何时询问用户、何时调用工具、何时停止？

1. 写状态与返回结构，区分已知事实、诊断假设、缺失信息。
2. 实现“信息不足 → 澄清；信息足够 → 检索；证据不足 → 返回不确定或有限重试”。
3. 设置最大工具调用数、超时和明确停止原因，记录真实工具参数与结果。
4. 增加会话 ID，测试两个会话不串历史；多知识库权限可留到后续阶段。
5. 在同一开发集上比较 Agent 与第 3 周基线，记录质量、耗时和调用量。

交付：诊断 Agent v0.1、三类路径样例、工具记录、基线对比。
验收：至少覆盖澄清、正常诊断、工具异常、预算耗尽；不得伪造“已执行测试”。
面试自问：Agent 多走了几步，究竟改善了哪些用例？

## 第 5 周：接入 DeepEval

学习问题：哪些结果可用代码判断，哪些需要人工或模型评分？

1. 在本项目环境安装并记录 DeepEval 版本，先验证一条数据转换。
2. 实现 adapter，将真实答案、检索上下文和工具调用转换为评测输入。
3. 先加入确定性规则，再选择工具正确性、答案相关性等需要的指标。
4. 累积约 30 条人工审核案例，按问题家族划分开发集、回归集、保留集。
5. 人工复核至少 10 条评分，记录裁判误判、环境错误和不适用项。

交付：DeepEval 适配、首份评测报告、用例版本、评分规则版本。
验收：正确和错误的对照样本能得到合理区分；actual_output 来自真实执行；裁判失败显式标错。
面试自问：工具名正确但参数错了，怎么发现？裁判分数可信吗？

## 第 6 周：加入一个贴近日常研发的工具

学习问题：工具是否真正减少定位时间？

1. 从读取 diff、解析 pytest/JUnit 报告、搜索指定项目代码中只选一个。
2. 为工具定义结构化输入输出，先写正常、格式错误、文件缺失测试。
3. 将工具接入 Agent，让它引用实际输出的文件位置或失败条目。
4. 采集 5 条新的真实任务，测量人工处理和辅助处理耗时，同时记录人工修正量。
5. 把已确认的失败加入回归集，重新比较第 4 周版本。

交付：一个可用工具、5 条实际使用记录、错误分类与对比报告。
验收：结论可以回查到日志/diff；只能访问选定项目；解析失败不能包装成“无问题”。
面试自问：工具失败与任务失败为什么要分开？

## 第 7 周：回归自动化与发布前检查

学习问题：怎么知道一次改动没有破坏原有行为？

1. 固定依赖、模型配置、Prompt、知识库和用例版本。
2. 建立快速测试层：普通单元测试 + 模拟工具集成测试。
3. 建立显式触发的模型评测层，配置凭据、预算、超时和报告产物。
4. 将关键业务失败与基础设施错误设为阻塞；跳过和波动单列，不能算通过。
5. 在自己创建的分支注入一个已知错误，确认检查失败；恢复后重新验证。

交付：可复现运行命令、CI 配置、一次红→绿验证、版本清单。
验收：全新环境能按说明运行；空数据集、缺凭据、执行异常不会产生“全通过”。
面试自问：为什么平均分提高仍可能不允许发布？

## 第 8 周：小范围使用、复盘与求职展示

学习问题：它解决了谁的问题，证据是什么？

1. 连续使用至少 5 个学习/开发时段，记录辅助有效、无效和误导案例。
2. 冻结本轮配置，运行一次保留集；失败可查看但不立即针对它调参后继续称盲测。
3. 选择一个效果明显的修复，写问题→假设→改动→结果→局限的实验总结。
4. 录制 3–5 分钟演示：一个正常任务、一个失败任务、一次回归对比。
5. 整理上游来源、个人贡献、指标定义和后续计划。

交付：v0.1 发布说明、演示、评测报告、贡献清单、下个月任务。
验收：别人能从 README 重现一个案例；没有伪造用户规模、提效百分比或原创范围。
面试自问：最难定位的失败是什么？你如何证明确实修好了？

## 第 9 周起：长期维护方向

- Agent 开发：完善持久化、流式返回、工具恢复、上下文压缩，逐项验证。
- Agent 评测：做裁判校准、难例分层、重复运行、漂移监测与失败聚类。
- 测试开发：接入 API/浏览器回归，验证真实业务状态，维护失败复现与稳定性。

每月只选一个方向的一个主题；数据和接口保持统一。任何架构升级都要与现有基线比较。

## 每周共同完成标准

- 有一次实际执行与记录。
- 有一条新失败或反例分析。
- 能脱离教程解释本周代码。
- 提交/变更中可区分上游已有能力和个人新增能力。
- 下周第一个任务具体到文件或可观察行为。
