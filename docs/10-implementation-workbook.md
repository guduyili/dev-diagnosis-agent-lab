## 2. 每个学习时段怎么做

### 120 分钟固定节奏

| 时间 | 操作 | 当场留下的证据 |
|---|---|---|
| 0–10 分钟 | 从本手册选一个最小任务，写输入、输出和失败条件 | 一张任务卡 |
| 10–30 分钟 | 只读相关函数及直接调用者；运行前先预测行为 | 预测和函数契约 |
| 30–45 分钟 | 用一个小输入执行或调试，查看关键变量 | 实际结果与预测差异 |
| 45–90 分钟 | 关闭源码，自己实现一个函数或行为；可查官方接口文档 | 自己的代码与设计理由 |
| 90–110 分钟 | 执行正常案例和一个针对性反例，比较上游处理 | 结果、错误层和修正 |
| 110–120 分钟 | 写复盘；明确下次从哪个文件和输入开始 | 日记与下一任务 |

遇到困难时先把问题缩小。例如“Agent 跑不通”缩小为“固定一个假模型响应，路由是否走到 tools”。不要一边换模型、一边换 embedding、一边改 Prompt。

每次查 AI 前先写三句话：我预期什么、实际发生什么、我怀疑哪一层。AI 可帮你解释和审查；关键函数完成后应能逐句说明。

### 一个模块算学会的四项检查

- 解释：说出输入、输出、副作用和异常，而不只描述每行语法。
- 实现：不看原实现写出最小等价行为。
- 反例：给出一个会破坏该行为的输入，并观察到预期失败。
- 迁移：需求变化时能改动，例如“支持版本过滤”或“限制工具参数”。

次日花 10 分钟回忆昨日的数据流；一周后换一个输入复做。靠回忆暴露理解缺口，比重复通读更有效。

### 笔记写什么

沿用 [任务模板](templates/task.md)、[日记模板](templates/daily.md)、[实验模板](templates/experiment.md)、[故障模板](templates/incident.md) 和 [决策模板](templates/decision.md)。

源码阅读笔记只需六项：来源 SHA 与函数、解决的问题、输入输出、关键分支、自己的反例、准备如何迁移。不要把整份源码粘进笔记当作学习成果。

### 六个容易看懂表面却理解错的地方

1. **澄清中断**：本地 `request_clarification` 返回空字典；图在编译时用 `interrupt_before` 暂停。继续阅读调用端如何更新同一会话状态并恢复，不能认为“函数返回一段文字”就等于完成澄清机制。
2. **状态合并**：`AgentState.tool_call_count`、`iteration_count` 使用累加 reducer。已有 2 次、节点返回增量 1，应得到 3；若返回累计值 3，就可能得到 5。普通覆盖字段需要另看其定义。[LangGraph 状态与 reducer 文档](https://docs.langchain.com/oss/python/langgraph/graph-api)
3. **工具计数**：上游 `orchestrator` 根据模型响应中的 `tool_calls` 增加计数，路由检查之后才可能执行工具。这是提出的调用数量，不等同于实际执行成功数量。
4. **结束条件顺序**：`route_after_orchestrator_call` 先处理“没有工具调用”，再检查有工具请求时的预算。边界上允许最终回答，与继续执行工具是不同决策。
5. **重复资料**：`add_documents` 按目标 Markdown 是否存在决定跳过。两个目录里的同名文件、同名但更新的内容是否符合你的需求，要通过实验确认；不能直接将此解释为内容去重或完整版本管理。
6. **模型与索引分开**：聊天模型配置和 embedding 配置独立。embedding 变化需要重新检查索引；即使向量维度一样，也不表示两个模型的向量语义兼容。

前四项可以先用假模型/手写状态实验验证。工具预算必须先检查再执行；对一个响应提出多个调用的情况，也要明确整批拒绝还是只执行允许部分，并留下选择理由。

## 5. 第 1 周：观察真实请求，形成可验证的问题

对应原任务 W01-01～W01-04，建议 8–12 小时。

### 做三个小任务

1. **W01-A，约 2 小时：登记现场。** 核对参考 SHA、未提交改动、解释器、模型与 embedding 配置；给 top-k、分块大小、迭代上限、工具上限各写一句解释。读取配置不等于验证服务可用。
2. **W01-B，约 3–5 小时：追踪一条请求。** 用自选的简短 Markdown 建立最小资料集，先观察查询改写，再观察检索工具、父块回取和最终答案。每一步记输入摘要、输出摘要、来源及错误；遇到阻塞就缩成独立调用排查。
3. **W01-C，约 3 小时：收集问题。** 建立 5 条真实问题记录，分别标注“已复现”“原因待确认”“修复待验证”等。资料不足就先少收集，不把编造问题计入真实数量。

### 第一条案例就用这次 400

将 `This response_format type is unavailable now` 记成 incident，关联触发的 `with_structured_output`、环境中的 SDK 版本和当前兼容修改。记录已验证的层级：语法 → 导入 → 请求构造 → 在线请求 → 完整流程。未验证层保持待验证。

为后续回归设计两个不同实验：

- 离线：在 SDK 传输边界捕获请求，确认实际载荷不携带导致此次错误的 `json_schema` 格式，并包含预期的工具定义；只看源码字符串不足以验证序列化行为。
- 在线：用一个最短问题完成结构化结果解析，保存脱敏结果、模型配置、SDK 版本和时间。该实验需要有效凭据，成功与否取决于实际运行。

仅有同一条错误文字时，不强行输出已确认根因；允许请求 SDK、调用方式或版本信息。明确补充资料后再判断。

### 本周验收

画出清晰问题、待澄清问题、无证据问题的三条流程；说明每次模型调用做什么；保留至少一次真实执行记录或定位清楚的阻塞。尚未修复的案例照实记录。

## 6. 第 2 周：资料、数据结构和有价值的普通测试

对应 W02-01～W02-04，建议 8–12 小时。

### 做三个小任务

1. **W02-A，约 2–3 小时：字段与加载。** 先选 3 份小文档写 loader，再扩到 10–20 份。选一种可解释的 ID 规则，例如“项目 + 相对路径”生成 document_id；内容哈希单独标识修订。
2. **W02-B，约 3–5 小时：基础切分。** 按 Markdown 标题或段落切分，暂不照搬上游所有合并函数。用“标题 + 短段落 + 代码围栏 + 异常栈”人工检查边界；说明超长代码块保留还是切分及代价。
3. **W02-C，约 2–4 小时：反例和用例。** 为确实影响检索的边界写测试，整理约 10 条人工审核开发用例；不够真实案例时，允许另标 constructed，分别统计。

### 先写这些行为测试

| 输入变化 | 希望验证的行为 |
|---|---|
| 缺失文件 | 明确报告读取错误，不能当成空资料成功 |
| 空文档 | 按已定契约跳过并记原因，或拒绝入库 |
| 不同目录同名文件 | document_id 不冲突 |
| 同一文档重复加载 | 不意外产生重复内容 |
| 同一文档内容更新 | 修订标识变化，旧索引处理方式明确 |
| 缺少 source/version 等必需元数据 | 验证失败；不能生成不可追溯证据 |

chunk_id 可结合文档修订、切分策略版本和块序号生成；相同输入及策略应可复现。切分策略变化时 ID 变化合理，但必须关联对应的索引和实验版本。

### 本周验收

随机选 3 个块，能回到原资料及对应版本。故意去掉一项必需来源信息，测试确实失败，恢复后通过。提交到评测集前按 [用例约定](../data/cases/README.md) 审核 id、family_id、origin、review_status、input、expected、source_refs。

## 7. 第 3 周：可比较的普通 RAG 基线

对应 W03-01～W03-03，建议 8–12 小时。

### 做三个小任务

1. **W03-A，约 3–4 小时：索引与检索。** 使用一个固定 embedding 和独立的学习索引；先实现 `search(query, k, project_id, project_version)`，返回有来源的结果。保存资料哈希、embedding 标识、切分配置、索引版本。
2. **W03-B，约 3–4 小时：单次生成。** 写 `baseline.diagnose`：输入检查 → 一次检索 → 生成带证据的回答。先用固定检索结果和假模型验证数据流，再做在线调用。空证据走已定义的不足分支。
3. **W03-C，约 2–4 小时：一次单因素实验。** 固定知识库、模型、Prompt 和问题集，只比较 k=3 与 k=5，逐条保存召回、生成上下文、答案、耗时和调用次数。数值是实验起点，不是最优参数结论。

### 怎么判断检索出了什么问题

先为有答案的问题标注期望来源。在同一粒度下计算：

- Hit@k：前 k 条是否至少命中一个人工标注的相关项。
- Recall@k：前 k 条命中的相关项数 / 人工标注的相关项总数；不知道完整相关集合时不声称测得完整召回率。
- 若只标了文档就按文档评，不把文档命中与 chunk 命中混算。无答案问题单列，不强行计算召回率。

看完整失败链：知识库有没有资料 → 切分后关键内容是否保留 → 是否召回 → 是否交给生成器 → 是否正确使用。分别记录知识缺失、召回失败、上下文遗漏、生成错误、基础设施错误。

### 父子分块与混合检索何时加

基础检索稳定后，选择一个“子片段命中但缺上下文”的案例，增加 parent_id 与父块回取，再比较“仅 child”与“child + parent”。确认父块去重与上下文长度。

BM25 + 向量混合检索作为另一个实验，不能与父子分块同时修改后统一归因。若检索返回分数，记录检索方式和分数含义；不要跨检索方式直接套用同一个阈值。

### 本周验收

10 条开发问题有可回查的逐条记录；普通 RAG 可脱离 UI 调用；实验可按保存配置重跑。报告写清小样本限制，不以平均分掩盖具体退化。

## 8. 第 4 周：状态、澄清和有限工具循环

对应 W04-01～W04-03，建议 8–12 小时；这是主要难点，可拆成两周。

### 做三个小任务

1. **W04-A，约 3–4 小时：状态与路由。** 先写普通 Python 路由函数，使用假分析结果验证 answered、needs_clarification、insufficient_evidence 等分支，再接入 LangGraph。初期用单 Agent、顺序执行。
2. **W04-B，约 3–5 小时：工具与预算。** 实现检索、父块回取两个工具的结构化结果；记录 proposed、executed、succeeded 三种数量。设置工具预算、迭代预算、模型请求超时和重试上限，明确各计数含义。
3. **W04-C，约 2–3 小时：恢复与对比。** 同一会话补充信息后恢复未解决问题；另一个会话不得读到它。用与基线相同的开发集比较质量、成本和耗时。

图状态、节点和条件边的 API 以安装版本为准，先把“覆盖还是合并”的语义理解清楚，再写框架代码。[LangGraph 官方图 API](https://docs.langchain.com/oss/python/langgraph/graph-api)

### 明确本项目自己的停止策略

初期可设最多 3 次实际工具调用、最多 5 轮决策作为练习值，实验后再调整。工具批次超过剩余预算时先整体拒绝，避免初期引入部分执行的复杂性。请求的时间限制与任务总时限分别处理。

一次模型请求超时与整体任务超时不是同一件事；所有 SDK 自动重试也要纳入记录。不能用无界重试修复确定性的 400 配置错误。fallback 若还调用模型，也计入模型调用及总时限。

对无法保证取消的阻塞工具调用，记录能力限制；不要仅设置一个字段就宣称实现了硬超时。W06 的本地报告解析可以先规定输入大小并单独验证。

### 路由验收矩阵

以下是拟实现的个人行为规范，不声称上游全部已有这些状态：

| 场景 | 期望行为 | 验证层 |
|---|---|---|
| 问题清楚且有证据 | 检索后 answered，引用来自实际证据 | 假模型集成 + 在线抽样 |
| 缺少必要版本或错误信息 | needs_clarification，说明缺什么 | 路由测试 |
| 完成有限检索仍无证据 | insufficient_evidence，不编造根因 | 假工具集成 |
| 父块不存在/检索接口异常 | 显式工具错误或按已定恢复规则处理 | 故障注入 |
| 本轮提出的工具调用超过剩余预算 | budget_exceeded；超额调用未执行 | 工具执行次数断言 |
| 已到边界但直接给出最终回答 | 按预定策略允许结束，且没有额外工具执行 | 边界测试 |
| 会话 A 在澄清时，会话 B 开始 | B 不使用 A 的事实；A 能独立恢复 | 双会话测试 |

内存 checkpointer 不能被描述为进程重启后的持久化。先验证进程内会话隔离，再把持久化列为后续任务。

### 本周验收

至少留下澄清、正常回答、工具失败、预算停止四种实际测试轨迹；能解释每一步状态变化。逐条指出 Agent 相对 W03 基线修好了什么、破坏了什么；不能假定流程更复杂就更好。

## 9. 第 5 周：DeepEval 与人工校准

对应 W05 任务，建议 8–12 小时。

### 做三个小任务

1. **W05-A，约 2–3 小时：用例加载和 adapter。** 加载人工审核用例，只将 `input` 送给 `diagnose`；将真实结果交给评分器。先验证 1 条转换，再跑 5 条。
2. **W05-B，约 3–4 小时：两层检查。** 先做字段、状态、来源存在性、工具参数和预算的确定性断言，再接一个语义指标。首个候选为 Faithfulness，评估回答与实际上下文的支持关系。
3. **W05-C，约 3–5 小时：人工校准和报告。** 汇总约 30 条经过审核的案例，按 family_id 划分开发、回归、保留集；人工评至少 10 条，与裁判结果逐条比较。

安装主项目所需的 DeepEval 版本并记录锁文件；业务模型配置不会自动成为评测裁判配置。先验证裁判的一次真实调用，尤其要独立核实它的结构化输出兼容方式。

### adapter 字段映射

| DeepEval 字段 | 来源 | 不应混入 |
|---|---|---|
| input | 用例的用户可见问题及必要上下文 | expected、评分标准 |
| actual_output | 本次真正生成的 answer | 人工答案或提前写好的“实际输出” |
| expected_output（适用时） | 已审核的人工参考 | 未核验的自动生成参考 |
| retrieval_context | 被测范围内实际召回并提供给生成器的上下文 | 标准答案、未召回资料、事后补齐证据 |
| tools_called（适用时） | 实际执行记录，保留参数和状态 | 仅由模型提出但未执行的调用 |

DeepEval 的测试对象支持分别传入实际输出、参考输出、检索上下文及工具调用；字段要与被评测的交互范围一致。[官方测试用例文档](https://deepeval.com/docs/evaluation-test-cases)

如果要独立评检索器，使用该检索器的原始召回；如果评最终生成环节，就记录实际送入该环节的上下文。存在压缩时同时保存原始证据与压缩内容，额外检查压缩是否引入错误，不能只保留最终答案引用。

Faithfulness 关注回答是否得到上下文支持；它不证明知识库内容本身正确或适用于当前项目版本。[官方 Faithfulness 文档](https://deepeval.com/docs/metrics-faithfulness)

### 报告与验收

- 每条结果保留 case_id、业务状态、评分结果、评分理由、耗时和配置版本。
- 区分 passed / failed / error / skipped / not_run；模型调用失败不能伪装成业务低分，裁判失败不能算通过。
- 对没有有效答案/上下文的错误任务，相关语义指标标 N/A，任务错误仍进入总数和门禁。
- 正确、错误、部分正确、应澄清四类样本有人工对照；先观察分数，再基于数据确定阈值。
- 输出一张 baseline/candidate 逐条变化表，不只给平均分。

按 [评测规范](05-evaluation.md) 记录案例、知识、索引、Prompt、模型、裁判、依赖和代码版本。保留集不用于日常调参；同一事故的不同措辞不跨集合。

## 10. 第 6 周：一个真实研发工具

对应 W06 任务，建议 8–12 小时。默认练习选“解析已经生成的 pytest JUnit XML 报告”，范围比自动执行测试更容易验证。

### 做三个小任务

1. **W06-A，约 3–4 小时：独立解析器。** 精读真实报告，定义输入为选定报告路径，输出包含测试项、失败/错误/跳过信息、耗时和可用的错误摘要。支持你实际遇到的 testsuite/testsuites 结构，明确未支持格式。
2. **W06-B，约 2–3 小时：工具集成。** 使用结构化输入输出接入 Agent；让答案引用具体测试项和报告证据，再检索历史排障笔记。
3. **W06-C，约 3–5 小时：实际使用。** 收集 5 次真实排障任务，记录辅助建议、人工修正和最终结果。资料不足时允许 pending，不提前填成功率。

### 核心测试

- 报告正常、缺失、XML 损坏、没有测试项。
- failure、error、skipped 分别保留，不能都压成“失败”或“通过”。
- 重名测试项用文件/类/参数化标识区分，记录报告生成时间和关联版本。
- 工具仅解析已有报告，回答只能声称“读取到报告结果”；不能声称“刚刚替你执行了测试”。

单元测试可以使用标注为 constructed 的小 XML；真实提效记录必须来自实际任务。先人工做再借助 Agent 做同一任务会产生熟悉效应；早期优先描述工作步骤和修正量，时间差只作观察值。

### 本周验收

有一条能回到报告测试项的诊断链路；解析错误没有被包装成“全部正常”；新发现的失败有对应回归案例。

## 11. 第 7 周：可重复的回归与检查失败演练

对应 W07 任务，建议 8–12 小时。

### 做三个小任务

1. **W07-A，约 2–3 小时：分层执行。** 普通测试和假模型集成测试默认不联网；在线业务运行与裁判评测单独触发。为环境、数据与配置生成运行清单。
2. **W07-B，约 3–4 小时：失败退出规则。** 实现实际的回归入口，明确哪些失败阻塞。缺凭据、空数据集、执行错误不能变成绿灯；跳过写明未覆盖范围。
3. **W07-C，约 3–5 小时：红→绿演练。** 在个人练习分支故意移除版本过滤或放宽工具预算中的一项，观察相关测试失败；恢复后再跑同一检查，保存前后证据。

优先对稳定的关键行为设门禁。语义分数波动较大的案例先重复运行并人工核查，不能靠降低阈值掩盖退化。官方 DeepEval 测试入口参见 [CI 文档](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd)。

### 本周验收

新建一个独立环境能按文档运行；已知错误能被检测；全 error、全 skipped、零用例不会被报告为全部通过。记录重复运行和缓存策略，避免把缓存命中误解为新的模型结果。

## 12. 第 8 周：独立讲解、真实使用和下一轮维护

对应 W08 任务，建议 8–12 小时。

1. 连续使用至少 5 个开发时段，记录有效、无效和误导建议，以及人工最终处理结果。
2. 冻结配置后运行保留集；如果看到结果后开始修正，就标记该集已经暴露，不再作为未见测试集反复报告。
3. 选择一个真实改进写完整实验：问题 → 假设 → 最小改动 → 对照 → 结果 → 局限。
4. 做 3–5 分钟演示：一个成功案例、一个主动澄清或停止案例、一个失败被回归发现的案例。
5. 整理个人贡献：哪些来自上游、哪些改写、哪些新增；移植部分保留来源和许可信息。

### 结业自测

给自己一个没有见过的报错描述，先说清需要的资料和评测标准，再判断现有系统是否能处理。允许输出“资料不足”；重点是行为有依据、结果可验证。

不看源码回答：为什么先做普通 RAG？什么场景需要父块？reducer 会怎样出错？工具请求和成功执行有什么差别？一个模型评分为什么不能代表整体通过？最近一次修复如何证实没有退化？

## 13. 按岗位调整后续投入

共同基础完成后，每月选一个主题：

| 方向 | 优先延伸 | 适合展示的成果 |
|---|---|---|
| Agent 开发 | 持久化恢复、工具错误恢复、并行子任务、上下文压缩 | 故障前后 trace、恢复行为与成本对比 |
| Agent 评测 | 难例分类、裁判校准、重复运行、组件级归因 | 人工与模型分歧表、版本退化分析 |
| 测试开发 | 报告聚合、契约测试、故障注入、CI 可靠性 | 红→绿复现、错误状态覆盖与可重跑记录 |

增加并行任务前，先验证单任务能稳定结束；增加记忆压缩前，先构造上下文过长导致失败的案例；更换 embedding 前，先建立固定的检索对照集。

## 14. 调试时用的分层顺序

| 现象 | 先检查 | 最小实验 |
|---|---|---|
| API 返回 400 | provider/模型、序列化请求、结构化输出方法 | 一个短输入的单独模型调用；不经过完整图 |
| 检索为空 | 索引是否有内容、版本过滤、查询、阈值、embedding | 直接调用 search，打印脱敏结果 |
| 检索有内容但回答错 | 实际生成上下文、版本、Prompt、引用 | 固定上下文，仅运行生成器 |
| Agent 不停调用工具 | 计数更新、路由顺序、重复调用、结束消息 | 假模型持续请求工具，观察何时停止 |
| 澄清后丢失原问题 | 同一会话标识、pending 状态、恢复逻辑 | 两轮固定输入，不引入长历史 |
| DeepEval 无结果 | 业务运行是否完成、adapter、裁判配置、异常状态 | 一个真实结果 → 单条评分 |
| 评分提高但使用更差 | 关键退化案例、错误覆盖、成本、数据泄漏 | 看逐条对照和人工判断 |

换模型或换框架应是有证据的实验，不作为所有错误的默认解决方案。

## 17. 如何请 AI 帮忙而保留学习过程

第一次阅读：

> 我正在学习函数 X。请先说明输入输出和它在调用链中的位置，再给我一个能手算的小输入。不要直接给完整重写版本；让我先预测结果，再检查我的解释。

> 请按本手册的阶段验收审查我的 diff、实际测试输出和笔记。指出没有证据的结论，并出三个迁移问题，验证我能否脱离教程解释实现。

代码跑通后：

> 请给出一个最可能暴露我当前实现缺陷的反例，说明它检验哪条行为约定。先让我设计测试，不直接替我生成所有测试代码。
